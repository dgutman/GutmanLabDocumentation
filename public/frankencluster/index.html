1. What Is a Frankencluster?

Most homelab clusters are uniform — same node, same drives, same everything. This is the opposite. The Emory Pathology Frankencluster is a living laboratory of hardware heterogeneity, spanning fourteen Proxmox nodes across three generations of server hardware, four drive classes, and five storage architectures — all in one Ceph cluster.

It wasn't designed this way. It evolved — each node was a hand-me-down, a surplus find, or a temporary measure that became permanent. And somehow, it works. Sometimes brilliantly.

⚡ The Core Idea

Run a production-adjacent Ceph cluster where HDDs, SATA SSDs, NVMe, and Optane-backed SSDs coexist under a single CRUSH hierarchy. Tune each device class independently. Benchmark everything. Document what breaks and how you fix it.

4.3 NVMe Tier Deep Dive

The NVMe tier uses 10 Intel P3600 1.6 TB drives spread across 6 nodes. These are PCIe 3.0 drives — modern but not cutting-edge. The 8,320 write IOPS number needs context:

  • 3× replication: every write is stored 3 times — raw 25K write IOPS per drive
  • rados bench at 16 threads — NVMe can handle 64–128+ queue depth
  • 32 PGs across 8 OSDs — increasing to 128–256 PGs would improve parallelism
  • MTU 9000 was a game-changer: ~10× improvement over MTU 1500 in earlier tests

4.4 Optane-Backed Tier (ceph_optane)

8 OSDs where a 3.49 TB SATA SSD is paired with a dedicated 64 GB NVMe partition for BlueFS DB. The NVMe DB accelerates metadata operations and small writes dramatically while the SATA SSD provides the capacity. This tier targets workloads needing lower latency than pure SSD but without the cost-per-GB of all-NVMe.

Benchmark data for this tier is pending — earlier Optane pool configuration issues were identified and the pool is being rebuilt for proper characterization.

6. The Icarus Optimization — How 3 Settings Killed 11× Performance

This is the highlight reel. Icarus (daghome pool) had a simple setup: 8× SATA SSD in 4 mirrors + 2× NVMe mirror for metadata (special vdev) + a 120 GB Intel NVMe SLOG. Sequential writes should have been screaming. Instead, they crawled at 375 MiB/s.

📖 For the full story with code samples and TrueNAS tuning commands, see our detailed blog post.

🔴 Before

375 MiB/s sequential write — something was very wrong

6.1 Three Compounding Bottlenecks

🔧 Bottleneck #1: special_small_blocks=128K + recordsize=16K

Every file block (16 KB) was under the 128 KB threshold, so ALL writes were diverted to the 2× NVMe special vdev mirror. The 8× SATA SSDs sat idle for writes. The NVMe special became a bottleneck it was never meant to be.

Fix: special_small_blocks=0 — metadata only goes to NVMe, data spreads across the main pool.

Result after fix: +27%

🔧 Bottleneck #2: logbias=latency

This setting forces EVERY write through the ZIL/SLOG — even async writes that should bypass it. With a single 120 GB Intel NVMe as SLOG, this created a hard ~360 MB/s bottleneck. logbias=latency is correct for NFS databases with sync writes, but disastrous for general file serving.

Fix: logbias=throughput — async writes bypass the ZIL entirely.

Result after fix: +40% cumulative

🔧 Bottleneck #3: zfs_dirty_data_max=4 GB

On a machine with 503 GiB of RAM, the default dirty data limit was 4 GB — a measly 0.8%. TrueNAS SCALE ships with this hard-coded rather than the traditional 10% of RAM. The transaction group throttle kicked in constantly, limiting bulk write throughput.

Fix: Raised to 32 GB (6% of RAM). Could go higher for write-heavy workloads.

Result after fix: +1,039% (11× improvement)

6.3 Key ZFS Lessons

  • special_small_blocks is powerful but dangerous. Combined with a small recordsize, it can accidentally turn the special vdev into the main write path, making it a bottleneck instead of an accelerator.
  • logbias=latency is for databases. Use it only when every write absolutely must survive a power loss. For home directories, NFS, and general file storage, throughput is correct.
  • TrueNAS SCALE ships with zfs_dirty_data_max=4 GB. On machines with >64 GB RAM, this is wildly conservative. Raise it to at least 10% of RAM for write-heavy workloads.
  • Benchmark with the right workload. direct=1 (bypasses ARC/page cache) vs psync (simulates NFS) can give 3× different results. Always test your actual access pattern.

10. Lessons Learned

This cluster has been running for years and every misconfiguration taught us something. Here's the curated list:

✅ Heterogeneity Works — With the Right Abstraction

Ceph's CRUSH device classes let you mix HDD, SSD, NVMe, and Optane-backed OSDs in a single cluster and route each workload to the right tier. This wouldn't work in a traditional RAID or SAN environment. The CRUSH rule + pool mapping pattern is the key architectural decision.

✅ MTU 9000 Matters — A Lot

Going from MTU 1500 → 9000 on the Ceph network showed ~10× improvement in some benchmarks. Every storage node should have jumbo frames configured on its storage VLAN.

✅ BlueFS DB/WAL Offloading Is a Force Multiplier

HDDs with dedicated NVMe for WAL (or DB+WAL) perform far better than their spinning rust peers. Our HDD tier achieves 2,299 write IOPS — competitive with SATA SSDs — thanks to this architecture.

⚠️ special_small_blocks: Read the Fine Print

This ZFS feature is easy to misconfigure. If your dataset's recordsize is smaller than special_small_blocks, every write goes to the special vdev, not the main pool. This turns your metadata accelerator into a bottleneck.

⚠️ TrueNAS SCALE's 4 GB Dirty Data Limit

A 4 GB zfs_dirty_data_max on machines with hundreds of GB of RAM creates constant transaction group throttling. This is a default that makes sense for embedded devices but not enterprise hardware. Raise it.

⚠️ Benchmark Scripts Lie — Verify Manually

Our Ceph benchmark script had a parsing bug that misreported IOPS. Always run a manual rados bench to validate automated results. The corrected numbers told a much better story than the buggy ones.

✅ Document Everything

The INFRA-BRAIN repository auto-generates agent-readable facts from live cluster snapshots. This has been invaluable for diagnosing issues and planning upgrades. Every OSD, every pool, every benchmark is tracked in version-controlled JSON.

✅ You Don't Need Uniform Hardware

This cluster runs 14 nodes with 4 different CPU generations, mixed RAM speeds, and 4 drive classes. It's stable, performant, and handles real research workloads. The secret is software-defined storage that abstracts the hardware away — Ceph and ZFS both excel at this. Don't let perfect be the enemy of good when it comes to homelab hardware.
